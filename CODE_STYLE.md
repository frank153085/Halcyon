# Halcyon Code Style

This document defines the repository-wide style for project-owned C++, HLSL, build, and
documentation files. The goal is predictable, readable code that is easy to review and
maintain while learning renderer architecture.

## Source language

- C++20 is required for project code.
- Use UTF-8 text, LF line endings, and a final newline.
- Use spaces, never tabs, for indentation.
- Keep source lines at or below 100 columns where practical.

## C++ formatting

Formatting is enforced by the root `.clang-format` file and LLVM as its base style.
Run Clang Format from the repository root:

```text
clang-format -i <files>
```

The important formatting rules are:

- Four-space indentation and four-space continuation indentation.
- Allman braces: the opening brace is placed on its own line.
- Left pointer alignment: `Type* value`.
- Control statements, short functions, loops, enums, and lambdas are expanded instead of
  being compressed onto one line. Empty functions and empty lambdas may remain compact.
- Function arguments and parameters are not bin-packed.
- Constructor initializer lists are never packed and use an eight-space continuation indent.
- Case labels are indented.
- Template declarations always break before the declaration.
- Brackets are not vertically aligned with the opening delimiter; indentation remains stable when
  arguments are added or removed.
- Missing control-flow braces are inserted by Clang Format where supported.
- Includes are sorted and regrouped. Keep the current file include, project includes, third-party
  includes, and standard-library includes in clearly separated groups when applicable.
- Namespace closing comments are maintained automatically.
- At most one consecutive empty line is kept.

Example:

```cpp
Result<void> Renderer::initialize(const RendererConfig& config)
{
    if (!config.enableValidation)
    {
        return Result<void>::success();
    }

    return createDevice(config);
}
```

## Static analysis

The root `.clang-tidy` enables compiler diagnostics and Clang Static Analyzer checks:

```text
clang-diagnostic-*
clang-analyzer-*
```

The known `NewDeleteLeaks` check is disabled because allocator ownership patterns can produce
false positives in low-level renderer code. Third-party and generated directories are excluded.
Warnings are initially reported without being promoted to errors so that learning work is not
blocked by a new diagnostic. CI may promote selected checks after the codebase is clean.

Run analysis with a compilation database (normally generated by CMake):

```text
clang-tidy -p <build-directory> <source-file>
```

Clang Tidy uses the repository `.clang-format` for any formatting fixes. Do not run it on
`ThirdParty`, `out`, or `cmake-build-*` contents.

## File and editor conventions

`.editorconfig` is the editor-independent baseline. It covers C++, HLSL, JSON, YAML, CMake,
Markdown, and plain text files. Keep trailing whitespace out of source files; Markdown may retain
trailing spaces when they are intentionally used for a hard line break.

Project-owned C++ headers use the `.h` suffix consistently. Third-party headers keep their upstream
suffixes. A public Halcyon header may be a thin forwarding facade to an internal header when it
provides a stable include path or hides backend details; forwarding headers must contain no logic
and must not duplicate declarations.

Public facades live under `Include/Halcyon/` and internal implementation headers live under
`Source/`. Application code should prefer the facade include path, for example
`#include "Halcyon/Application.h"` or `#include "Halcyon/Engine.h"`.

`.gitattributes` enforces LF text files and marks shader binaries, images, and compiled assets as
binary. Do not override these attributes for individual commits.

## Naming and API readability

- Prefer descriptive names over abbreviations, especially for synchronization, resource states,
  and GPU timestamps.
- Use `PascalCase` for types and public methods, `camelCase` for local variables and parameters,
  and a trailing underscore for private data members.
- Keep ownership explicit. Prefer RAII, stable handles, and `Result<T>` for fallible operations.
- Do not expose raw Vulkan handles from public renderer interfaces. Native handles may be used only
  through the backend command context escape hatch.
- Keep frame packets immutable after construction and avoid hidden per-frame global state.
- Comments should explain intent, invariants, or synchronization requirements rather than restating
  the code.

## Formatting scope

Clang Format ignores `ThirdParty/**`, `out/**`, `cmake-build-*/**`, and `.idea/**`. Generated files
should not be hand-formatted or committed unless the build explicitly requires them.

## Verification before a commit

From a clean build directory, run:

```text
clang-format --dry-run --Werror <project-files>
clang-tidy -p <build-directory> <changed-source-files>
cmake --build <build-directory>
ctest --test-dir <build-directory> --output-on-failure
git diff --check
```

Formatting and analysis changes should be kept separate from functional changes when possible.
